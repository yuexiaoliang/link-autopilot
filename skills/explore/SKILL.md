# 外链平台探索

**触发方式**：用户消息以 `/link-explore` 开头时激活。

发现、测试、验证新的外链铺设平台，将验证通过的平台注册到活跃平台池，供 [[link-autopilot]] 技能使用。

## 重要：与铺设 skill 的职责边界

| 职责 | link-explore（本 skill） | link-autopilot |
|------|------------------------|----------------|
| 发现新平台 | ✅ | ❌ |
| 测试平台可行性 | ✅ | ❌ |
| 注册平台账号 | ✅ | ❌（只复用已有账号） |
| 铺设外链到已知平台 | ❌ | ✅ |
| 更新 `platform-success-rate.md` | ✅（新平台条目） | ✅（铺设结果更新） |

**禁止在铺设任务中探索新平台**，也禁止在探索任务中执行大规模铺设。

## 探索触发条件

以下情况应启动平台探索：

1. **用户主动要求** — `/link-explore`
2. **已知平台池枯竭** — `platform-success-rate.md` 中活跃平台（成功率 >= 30%）少于 5 个
3. **内容类型不匹配** — 目标域名内容属性特殊，现有平台池中无匹配渠道
4. **定期巡检** — 建议每月执行一次，补充平台池

## 执行流程

### Step 1：读取当前平台池

执行前读取以下文件，了解已知平台全貌：

| 文件 | 读取内容 | 不读内容 |
|------|---------|---------|
| `platform-success-rate.md` | 各平台成功率、尝试次数、最后尝试日期 | **不读** API 格式、认证方式等技术细节 |
| `lessons/platforms.md` | 各平台 API 格式、认证方式、频率上限、注意事项、不可用平台列表 | **不读** 统计数据 |
| `.backlink-data/accounts.json` | 已有账号列表（避免重复注册） | |

**两个文件各司其职，不重复。** `platform-success-rate.md` 只存统计数据；`lessons/platforms.md` 只存技术细节和经验教训。

### Step 2：确定探索方向

根据目标内容类型，选择探索策略：

| 内容类型 | 探索方向示例 |
|---------|------------|
| 技术/开发者 | GitHub 生态、技术博客平台、开发者社区、开源聚合站 |
| 电商/消费 | 导购社区、评测平台、优惠券站点、行业垂直论坛 |
| 教育 | 课程平台、知识社区、学术资源站、教育论坛 |
| 本地生活 | 地图服务、本地点评、分类信息、同城社区 |
| 通用内容 | 内容农场替代平台、新兴社交媒体、海外论坛 |

**探索方法**（不限于此，Agent 可自主创造新渠道）：

- **邪修思维**：激活 [[xiexiu]] 技能，用非传统视角挖掘被主流 SEO 社区忽视的平台和渠道
- 搜索引擎：尝试不同关键词组合，如外链平台推荐、领域论坛列表、竞品外链分析等
- 社交媒体：Twitter/X、Telegram、Discord 中搜索相关讨论
- 行业资源：SEO 博客、数字营销社区、外链建设经验分享帖
- 竞品分析：查看竞争对手的外链来源，寻找被忽视的平台
- 语言/地域筛选：中文站优先中文平台，英文站优先英文平台，但也可跨语言寻找高权重机会

### Step 3：候选平台初筛

对发现的候选平台进行快速评估，过滤明显不合适的：

| 过滤条件 | 处理方式 |
|---------|---------|
| 已在已知平台池中 | 跳过 |
| 注册需要实名/企业资质 | 记录为"高门槛备选"，暂不测试 |
| 明确禁止外部链接（如部分问答平台） | 跳过 |
| 需要付费才能发布 | 记录为"付费备选"，标记成本 |
| 页面权重极低（新站/无流量） | 跳过 |

**重要：初筛通过 ≠ 平台可用。必须通过 Step 4 端到端实测才能判定。**

### Step 4：平台实测（不可跳过）

对初筛通过的候选平台进行**强制端到端测试**。Agent 必须实际完成注册、发布、验证全流程，不可仅凭理论分析判定平台可用。

#### 4.1 注册账号

**操作纪律：先执行，后记录。不可仅凭阅读平台页面就声称已完成。**

1. **检查现有账号**
   - 执行 `link-autopilot email list <platform>` 查看该平台是否已有 `status: active` 的账号
   - 有可用账号 → 直接使用，跳过注册

2. **生成邮箱**
   - 调用 CLI：
     ```bash
     link-autopilot email generate <platform>
     ```
   - 拿到输出的邮箱地址（如 `github-gist-3@llmrank.top`）

3. **打开浏览器执行注册**
   - 使用 chrome-devtools MCP **实际打开**平台注册页面
   - 使用生成的邮箱、填写用户名密码、提交表单
   - **截图或页面快照**作为已执行的证据

4. **获取验证码**
   - 通过 [[colonymail]] **实际读取**统一收件箱中的验证码邮件
   - **截图或记录邮件内容**作为证据
   - 提取验证码并在注册页面完成验证

5. **记录账号信息**
   - 将注册信息写入 `.backlink-data/accounts.json`：
     ```json
     {
       "github-gist": {
         "accounts": [
           {
             "email": "github-gist-3@llmrank.top",
             "username": "xxx",
             "password": "xxx",
             "status": "active",
             "createdAt": "2026-05-28"
           }
         ]
       }
     }
     ```

#### 4.2 发布测试内容

**操作纪律：先执行，后记录。必须实际提交内容，不可仅描述发布流程。**

1. **实际登录**
   - 使用 chrome-devtools MCP 打开平台并登录已注册的账号
   - **截图确认已登录**

2. **创建并提交内容**
   - 实际进入内容发布页面
   - 创建包含测试链接的内容（链接指向如 `https://example.com/test-link-explore`）
   - 实际填写标题、正文、插入链接
   - 实际点击发布/提交按钮
   - **截图或记录发布后的页面 URL**

3. **记录发布信息**
   - 内容格式要求
   - 审核时间（即时 / 数小时 / 数天）
   - 是否需要人工审批

#### 4.3 验证链接属性

**操作纪律：必须实际访问已发布内容的页面，不可仅凭发布时的界面推断。**

1. **实际访问内容页面**
   - 使用 chrome-devtools MCP 打开已发布内容的 URL
   - **截图或快照**页面内容

2. **检查链接属性**
   - **链接是否可见？**（硬性条件：不可见 = 无效）
   - **链接是否可点击？**（影响评分：可点击权重高，纯文本 URL 权重低但不一票否决）
   - **链接的 `rel` 属性**：`dofollow` / `nofollow` / `ugc` / `sponsored`？
   - **链接是否被重定向或缩短？**

#### 4.4 等待审核

- 记录审核时间（即时发布 / 数小时 / 数天）
- 若内容被删除/隐藏，记录原因和平台反馈

#### 4.5 评估平台价值

| 维度 | 评分（1-5） |
|------|-----------|
| 权重传递（dofollow + 高权威度 + 可点击） | |
| 审核门槛（注册和发布难度） | |
| 可规模化（能否批量操作） | |
| 综合评分 | |

#### 4.6 实测通过确认（必须逐项勾选）

Agent 必须在历史记录中确认以下项已完成：

**硬性条件（缺一不可，每项必须有截图或页面快照作为证据）：**
- [ ] 实际打开浏览器完成注册（非仅阅读注册页面）
- [ ] 实际发布含测试链接的内容（非仅描述发布流程）
- [ ] 实际访问已发布页面，验证链接**可见**
- [ ] 实际检查链接的 `rel` 属性
- [ ] 实际完成评分（1-5 分）

**评分参考（影响评分但不一票否决）：**
- [ ] 链接**可点击**（可点击 + 高分，纯文本 URL + 低分但仍可接受）

**综合评分 >= 3 且链接可见** → 进入 Step 5
**评分 < 3 或链接不可见** → 记录淘汰原因，**禁止进入活跃池**

### Step 5：注册到活跃平台池（仅实测通过的平台）

**未完成 Step 4 实测的平台，无论初筛看起来多合适，都禁止写入活跃池。**

验证通过的平台执行以下注册操作：

1. **更新 `platform-success-rate.md`**（只存统计数据）
   - 新增平台独立区块
   - 初始数据：总尝试 = 1，成功 = 1（探索成功），成功率 = 100%
   - 备注栏只写统计相关简短说明（如"首次探索成功"），**不写** API 格式、认证方式、字段名等技术细节

2. **更新 `lessons/platforms.md`**（只存技术细节）
   - 记录平台特性：域名、功能路径、认证方式、内容格式、频率上限、注意事项
   - 标记为"已验证可用"
   - **不写** 尝试次数、成功率等统计数据——那些只在 `platform-success-rate.md` 中更新

3. **更新 `lessons/rate-limiting.md`**（如测试中获得频率数据）

4. **记录探索日志**
   - 在 `.backlink-data/blast/history/` 中创建探索记录文件
   - 命名格式：`{日期}-{时分}-explore.md`

### Step 6：归档

在 `.backlink-data/blast/index.md` 顶部插入探索节点：

```markdown
- **{YYYY-MM-DD HH:mm}** | [explore] | 测试{n}个新平台，通过{m} | [详情](history/{文件名}.md)
  - 新平台：{平台名1}、{平台名2}
  - 淘汰平台：{平台名3}（原因）
```

## 输出物

每次探索结束后生成：

- `.backlink-data/blast/history/{日期}-{时分}-explore.md` — 本次探索完整记录
- `.backlink-data/blast/index.md` — 插入 [explore] 类型节点
- `.backlink-data/blast/platform-success-rate.md` — 新增验证通过的平台条目
- `.backlink-data/blast/lessons/platforms.md` — 更新平台特性说明
- `.backlink-data/accounts.json` — 新增注册账号信息

---

## 探索纪律

- **单次探索上限**：一次任务中测试的候选平台不超过 10 个，避免任务无限膨胀
- **失败即记录**：未通过验证的平台也要在探索记录中注明淘汰原因，避免重复尝试
- **不重复测试**：同一平台 30 天内不再重复探索（除非有明确信号表明规则已变）
- **保守注册**：优先使用临时/备用邮箱注册测试账号，避免主域名/主邮箱被封禁

## 平台命名规范

探索过程中发现新平台时自主命名，无需询问用户。
